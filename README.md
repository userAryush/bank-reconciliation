# Bank Statement Reconciliation Pipeline

An automation project that matches incoming bank payments to open invoices and books them into an ERP system, with safety checks so nothing is booked unless the system is confident.

> **Status: work in progress.** The synthetic dataset and the mock ERP API are done. The parser, matcher, decision logic, audit log and n8n automation are being built. See the [Roadmap](#roadmap).

> **Important:** all data is **synthetic**, and the ERP is a **mock** that follows a NetSuite-style REST pattern. No real bank data and no real NetSuite account are involved.

---

## The problem

Finance teams receive a bank statement every day: a list of money that arrived. Separately, the accounting system holds a list of **open invoices** (bills sent to customers that are not yet marked as paid).

Someone has to decide, for every bank line, *which invoice did this payment pay?*, and then record it in the accounting system. This is called **bank reconciliation** (or *cash application*). Done by hand, it is slow, repetitive and error-prone.

## What makes it hard

| Problem | Example |
|---|---|
| German number and date formats | `1.234,56` means 1234.56, and dates are `dd.mm.yyyy` |
| Invoice number buried in free text | `Zahlung Rg. Nr. INV-2025-0042 vielen Dank` |
| Name mismatches | `Müller GmbH` vs `MUELLER Gmbh` |
| Partial payments | A 1,000 EUR invoice paid with 400 EUR |
| One payment, several invoices | One transfer covering three invoices |
| Missing reference | Text says only `Zahlung`, so match by name and amount |
| Duplicate transactions | The same line appearing twice must not be booked twice |
| Unstructured PDF statements | Data has to be extracted from a PDF, not a CSV |

## The solution (target design)

```
Bank statement (CSV / PDF)
        │
        ▼
 1. EXTRACT   Rules first; an LLM only as a fallback for PDFs
        │
        ▼
 2. MATCH     Invoice-number regex + fuzzy name matching + amount logic
        │
        ▼
 3. DECIDE    High confidence → auto-book
              Medium         → human review queue
              Low / duplicate → reject
        │
        ▼
 4. BOOK      POST to the ERP REST API (idempotent, with retries)
        │
        ▼
 5. LOG       Audit trail, exceptions queue, alerts (n8n)
```

### Design principles

- **Rules before AI.** LLMs are slower, cost money and can be wrong, so they are used only as a fallback.
- **Confidence-based decisions.** The system books automatically only when it is sure. Everything else goes to a human.
- **Idempotent booking.** Retrying a request can never book a payment twice.
- **Money is `Decimal`, never `float`.**
- **One integration point.** Only `erp_client.py` will talk to the ERP, so replacing the mock with real NetSuite means changing that client and the field mappings.
- **Measurable accuracy.** A ground-truth file lets the matcher be scored as a number.

## The synthetic dataset

Generated by `data/generate_data.py` with a fixed seed (default `42`), so the same seed always produces identical files.

| File | Description |
|---|---|
| `open_invoices.csv` | 200 open invoices (`invoice_number`, `customer_id`, `customer_name`, `amount_eur`, `due_date`) for about 40 German-style companies, including deliberately similar names |
| `bank_statement.csv` | 120 transactions in German bank-export style (semicolon-separated, decimal comma, `dd.mm.yyyy` dates) |
| `ground_truth.csv` | The answer key: which invoice(s) each transaction belongs to, its scenario, and the expected action |

### Transaction scenarios

| Scenario | Count | Expected action |
|---|---|---|
| Exact match | 84 | auto-book |
| Name variation | 12 | auto-book |
| Partial payment | 10 | review |
| Multi-invoice payment | 6 | auto-book |
| Missing reference | 5 | review |
| Duplicate | 3 | reject |

`ground_truth.csv` has 127 rows, because one multi-invoice transaction maps to several invoices.

Regenerate or verify:

```powershell
python data/generate_data.py            # add --seed 7 to change the data
python data/check_data.py
```

## The mock ERP

A small Django REST API that behaves like the receivables module of an ERP.

### Models

| Model | Key fields |
|---|---|
| Customer | `customer_id` (unique), `name` |
| Invoice | `invoice_number` (unique), customer, `amount`, `due_date`, `status` (open / partially_paid / paid); `amount_paid` and `balance` are computed from payments |
| Payment | invoice, `amount`, `reference`, `idempotency_key` (unique), `booked_at` |

### Endpoints

All endpoints require token authentication (`Authorization: Token <token>`).

| Endpoint | Behavior |
|---|---|
| `GET /api/customers/` | List customers |
| `GET /api/invoices/?status=open` | List invoices; `status=unpaid` returns open and partially paid |
| `POST /api/payments/` | Book a payment |
| `GET /api/payments/` | List payments |

Example payment request:

```json
{
  "invoice_number": "INV-2025-0001",
  "amount": "100.00",
  "reference": "Rechnung INV-2025-0001",
  "idempotency_key": "abc-123"
}
```

### Business rules

- **Idempotency:** the same `idempotency_key` sent again returns the original payment and creates no second one.
- **Overpayment protection:** a payment larger than the invoice balance is rejected with `400`.
- **Paid invoices:** payments against an already paid invoice are rejected with `400`.
- **Atomic booking:** the payment is created and the invoice status updated in one database transaction, with the invoice row locked.
- **Status updates:** a partial payment sets `partially_paid`, and a full payment sets `paid`.

Note: SQLite ignores row locks, so the locking has a real effect only on PostgreSQL.

## Getting started (Windows PowerShell)

```powershell
# 1. Create and activate a virtual environment
python -m venv env
.\env\Scripts\Activate.ps1

# 2. Install dependencies
pip install -r requirements.txt

# 3. Generate the synthetic data
python data/generate_data.py

# 4. Set up the ERP
cd bank_erp
python manage.py migrate
python manage.py seed_erp
python manage.py create_service_user    # prints the API token for the 'reconciler' user

# 5. Run the ERP
python manage.py runserver
```

Create a `.env` file in the repo root (never commit it):

```
ERP_URL=http://127.0.0.1:8000
ERP_TOKEN=<token printed by create_service_user>
```

### Run the tests

```powershell
cd bank_erp
pytest
```

- It is a proof of concept, not production software. Real finance systems need much more security, compliance and monitoring.
